# 个人股票与基金持仓工具：代码调研与影响分析

> 状态：已完成只读调研，尚未修改业务代码。

## 1. 当前项目结构

当前产品是 Python 3.11+、Streamlit、SQLite 的单体应用：

```text
Streamlit dashboard
  -> 直接调用持仓、自选、分析等 Python 函数
  -> 直接执行 SQLite SQL
  -> 同步请求 AKShare、Yahoo Finance、腾讯等行情源
```

主要现状：

- `dashboard.py` 同时承担菜单、页面、CSS、表单和业务编排，接近 2,000 行。
- `src/stock_picker/db.py` 集中定义 SQLite 表、手写 SQL 和增量迁移。
- `src/stock_picker/portfolio.py`、`watchlist.py` 承担当前持仓和自选逻辑。
- `provider.py`、`analysis.py`、`multi_asset.py` 包含行情和基金净值处理经验。
- 根目录 `compose.yaml` 只部署一个 Streamlit 容器。
- 项目没有独立 Web 前端、HTTP API、用户认证、权限隔离、PostgreSQL 或 Alembic。
- 当前菜单约 30 个页面，与新产品只保留“持有、自选”两个核心入口的定位冲突。

## 2. 不能原地改造的原因

- 现有业务表没有 `user_id`，数据默认全局共享。
- 投资账户只是持仓上的自由文本，不是可管理的独立实体。
- 自选主键不支持用户隔离、多分组或同一资产进入不同分组。
- 资产仅以 `code` 或 `symbol` 标识，无法可靠处理未来不同市场的同代码资产。
- 金额、数量和成本使用 SQLite `REAL` 与 Python `float`，不满足账本精度要求。
- 基金持仓只支持份额和单位成本，不支持已确认的基金快速录入。
- 外部行情请求混在页面请求中，数据源变慢会直接拖慢页面。
- 页面、业务、数据库和第三方数据源没有稳定模块边界。
- 当前没有应用级认证，不适合直接开放公网自助注册。

结论：新产品应在当前新分支中建立独立应用结构，不在 `dashboard.py` 和旧 SQLite 表上渐进堆叠。

## 3. 可继承的业务规则

旧实现不直接作为新架构基础，但下列规则应重新实现并写成自动化测试：

1. 基金当前市值使用单位净值；累计净值不能代替单位净值。
2. 行情和净值保存来源、数据时间和抓取时间。
3. 行情失败时显示失败或陈旧状态，不生成替代数字。
4. A 股与基金使用不同定价适配器。
5. 外部数据源通过稳定接口隔离，允许回退或更换数据供应方。
6. 容器使用非 root 用户，业务端口只绑定回环地址，数据库不暴露公网。
7. 旧 SQLite 数据卷和备份在迁移决定前不得删除。

## 5. 一期核心数据影响

新数据模型至少需要：

- `users`：邮箱、密码哈希、用户状态。
- `sessions`：服务端不透明会话及失效时间。
- `investment_accounts`：用户的多个投资账户。
- `instruments`：市场、交易代码、资产类型、币种、交易所。
- `instrument_prices`：分别标识股票价格、基金官方单位净值和基金估算净值。
- `positions`：投资账户下的股票或基金持仓。
- `watchlist_groups`、`watchlist_items`：用户自选多分组。

基金持仓必须保留原始录入方式和原始字段，推算结果不能覆盖用户输入。为未来多市场预留：

- 资产以市场和市场代码联合识别，不只使用六位代码。
- 市场、交易所、币种、时区和交易日历使用独立字段。
- 金额使用 PostgreSQL `NUMERIC` 和 Python `Decimal`。
- 数据库存储 UTC 时间，展示时按用户时区转换。

## 6. 兼容性与 Breaking Change

新产品是用户已经明确要求的整体替换，以下内容最终会发生不兼容变化：

- Streamlit 页面和导航被 React Web 替代。
- SQLite 表结构被 PostgreSQL/Alembic 替代。
- 容器服务、健康检查和备份方式变化。
- 旧内部 Python 函数不作为新系统公开接口。

保留策略：

- Git 历史和当前主分支保留旧实现。
- 新系统通过独立端口和数据库并行验证。
- 新产品认证通过前保留现有 Caddy Basic Auth。
- 域名切换失败时把 Caddy 上游恢复到旧 Streamlit 服务。
- 在删除新分支中的旧文件或切换生产域名前，再次向用户明确说明并取得确认。

## 7. 数据迁移影响

旧 SQLite 持仓和自选缺少用户、正式投资账户与自选分组关系，不能无条件自动迁移。若需要迁移，必须确定：

- 旧数据归属哪个注册邮箱。
- 使用哪个默认投资账户和默认自选分组。
- 旧基金的 `quantity/cost_price` 如何映射为新基金精确录入。

推荐默认策略：完整备份并只读保留旧数据库，新系统使用全新 PostgreSQL；如用户确实需要，再提供一次性、显式执行的导入工具。

## 8. 安全和部署风险

- 公开注册需要 Argon2 密码哈希、安全 Cookie、CSRF 防护、登录/注册限流和防账号枚举。
- 每个查询只能从服务端会话取得用户 ID，不能信任客户端传入的用户 ID。
- 不强制验证邮箱时，输错邮箱会影响找回密码。
- PostgreSQL 只连接 Compose 内网，不映射公网端口。
- 旧 Streamlit、新 Web、新 API 和 PostgreSQL 使用独立端口或网络并行运行。
- 新服务健康检查、数据库迁移和核心流程通过后，才原子切换 Caddy 上游。
- 旧 SQLite 卷与新 PostgreSQL 卷完全分离，禁止使用 `docker compose down -v` 删除卷。
- 行情抓取不能阻塞 Web 请求，应使用缓存与独立刷新任务。
- 免费聚合行情存在延迟、限流、稳定性和授权范围风险，页面必须展示来源与时间。
