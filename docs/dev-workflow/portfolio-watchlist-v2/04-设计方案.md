# 个人股票与基金持仓工具：总体设计方案

> 状态：Phase 5 设计终版，用户已于 2026-08-24 确认
> 工作分支：`feature/portfolio-watchlist-v2`
> 集成目标：`dev2.x`
> 生产发布：`dev2.x` 验收后合并到 `main`，发布 `v2.x.y`

## 1. 目标与设计原则

一期只完成一件事：让个人投资者清楚、可靠地管理自己持有什么，以及正在观察什么。

设计原则：

1. **两个入口**：登录后一级业务菜单只有“持有”和“自选”。
2. **账本优先**：先保证持仓数据可信，再考虑分析、提醒和报表。
3. **数据不冒充**：股票价格、基金官方净值和基金估算净值明确区分并显示时间。
4. **用户隔离**：所有业务查询都由服务端会话确定用户，客户端不能指定数据归属。
5. **简单但可扩展**：使用模块化单体，预留市场、币种和数据源边界，不提前拆微服务。
6. **本地读取优先**：页面请求只读取本地数据库，不同步等待外部行情接口。
7. **可回滚发布**：新旧服务并行，域名切换失败时可以立即恢复旧服务。
8. **开源可维护**：契约、测试、文档、版本和贡献流程与代码同时建设。

## 2. 架构路径比较

| 路径 | 优点 | 主要问题 | 结论 |
|---|---|---|---|
| 原地改造 Streamlit/SQLite | 短期代码量少 | 无用户隔离、界面耦合、财务精度和扩展性问题仍存在 | 不采用 |
| 直接删除旧系统并一次切换 | 新代码最干净 | 上线风险高，失败后恢复困难 | 不采用 |
| 新系统独立建设并与旧系统并行 | 新架构干净、可逐步验证、可快速回滚 | 部署期短暂维护两套服务 | **采用** |

选择第三条路径。旧代码不作为新架构基础，但保留已验证的数据口径和安全原则；新系统通过独立目录、端口和数据库建设。

## 3. 技术栈

### 3.1 Web 前端

- React 19
- TypeScript
- Vite 8
- React Router 7
- TanStack Query 5
- CSS Modules + 全局设计令牌
- Vitest + Testing Library
- Playwright 端到端测试
- npm 锁定依赖版本

不使用大型 UI 套件和图表库。对话框优先使用现代浏览器原生 `<dialog>`，图标使用少量项目内 SVG，避免为了几个控件引入整套组件系统。

### 3.2 API 与任务进程

- Python 3.12
- FastAPI
- Pydantic 2
- SQLAlchemy 2.0 稳定系列
- Alembic
- psycopg 3
- `pwdlib[argon2]`
- pytest、pytest-cov、mypy、Ruff
- uv 锁定 Python 依赖

API 和后台行情任务使用同一套后端代码。任务进程是同一模块化单体的第二个运行入口，不引入 Celery、Redis 或微服务。

### 3.3 数据与部署

- PostgreSQL 17
- Nginx 静态文件容器
- 现有主机 Caddy 负责 HTTPS、压缩和反向代理
- Docker Compose 编排 `web`、`api`、`worker`、`postgres`
- SMTP 负责密码重置邮件

```text
  ▼

  └── 其他路径 ─────► Nginx 静态 React 应用

  ├── Auth                │
  ├── Portfolios          │
  ├── Watchlists          │
  ├── Instruments         │
  └── Market Data         │
           │              │
           ▼              │
       PostgreSQL ◄───────┘
           ▲
           │
Worker Scheduler ──► 外部行情/净值 Provider
```

关键约束：

- Web API 请求不直接调用外部行情源。
- Worker 只同步资产主数据以及用户持有、自选涉及的行情，避免全量高频抓取。
- 外部响应先经过 Pydantic 边界校验，验证失败时记录失败，不写入伪造或部分字段。
- 所有用户页面接口使用同源 Cookie，不开放宽泛 CORS。

## 6. 后端模块边界

每个业务模块内部使用 `models / schemas / repository / service / router` 分层：

| 模块 | 职责 | 不负责 |
|---|---|---|
| `auth` | 注册、会话、密码重置、安全事件 | 投资账户和业务权限 |
| `instruments` | 资产主数据、市场代码、搜索 | 用户持仓和估值 |
| `market_data` | 价格、净值、Provider 适配、数据新鲜度 | 用户输入和组合计算 |
| `portfolios` | 投资账户、持仓、成本和估值组合 | 外部数据抓取 |
| `watchlists` | 自选分组、标的、备注 | 持仓成本 |
| `jobs` | 跨模块同步编排、任务状态和调度锁 | 页面接口 |

依赖方向：

```text
api routers
  -> services
      -> repositories
      -> instruments contracts
      -> market_data read contracts

jobs
  -> instruments
  -> market_data
  -> portfolios/watchlists read contracts
```

业务模块不能相互导入对方的 ORM 内部实现；跨模块只使用明确的服务接口或只读契约。

## 7. 核心数据模型

所有主键使用 UUID；金额、份额和价格使用 PostgreSQL `NUMERIC`；时间使用 UTC `TIMESTAMPTZ`，基金净值同时保存业务日期。

| 表 | 关键字段 | 关键约束 |
|---|---|---|
| `users` | `email_normalized`、`password_hash`、`status` | 邮箱忽略大小写唯一 |
| `sessions` | `token_hash`、`user_id`、`expires_at`、`revoked_at` | 只存会话令牌哈希 |
| `password_reset_tokens` | `token_hash`、`user_id`、`expires_at`、`used_at` | 单次使用、短期有效 |
| `security_events` | 事件类型、主体哈希、时间、请求 ID | 不保存密码和完整令牌 |
| `investment_accounts` | `user_id`、`name`、`base_currency`、`sort_order` | 同一用户账户名唯一 |
| `instruments` | `asset_type`、`market`、`exchange`、`ticker`、`currency` | `asset_type + market + ticker` 唯一 |
| `instrument_prices` | `instrument_id`、`price_type`、`value`、`as_of_date/at`、`source` | 价格类型明确，不覆盖不同口径 |
| `positions` | `account_id`、`instrument_id`、录入模式、原始输入、规范化数量和成本 | 同一账户同一标的唯一 |
| `watchlist_groups` | `user_id`、`name`、`is_default`、`sort_order` | 同一用户组名唯一，默认组不可删 |
| `watchlist_items` | `group_id`、`instrument_id`、`note` | 同一组同一标的唯一 |
| `data_sync_runs` | 任务类型、状态、数量、错误摘要、起止时间 | 同步失败留痕 |

### 7.1 资产枚举

```text
assetType: STOCK | FUND
market: CN
exchange: SSE | SZSE | BSE | FUND_CN
currency: CNY
priceType: STOCK_LAST | FUND_OFFICIAL_NAV | FUND_ESTIMATED_NAV
positionInputMode: STOCK_SHARES | FUND_AMOUNT | FUND_SHARES
```

枚举值只允许新增，不改变已发布值的含义。未来港股、美股通过新增市场、交易所和币种实现。

### 7.2 持仓原始输入与规范化字段

`positions` 同时保留：

- 用户原始输入：金额、收益、份额、成本输入方式、数据日期。
- 规范化结果：数量、总成本、平均成本。
- 推算状态：数量是否估算、使用的官方净值和净值日期。
- 乐观锁版本：`version`，防止多个页面覆盖彼此修改。

前端不能直接写入系统推算字段；所有权威计算在后端服务完成。

## 8. 持仓计算规则

### 8.1 股票

用户填写数量，并在总成本和平均成本中选择一种：

```text
总成本 = 数量 × 平均成本
当前市值 = 数量 × 最新股票价格
持有收益 = 当前市值 - 总成本
收益率 = 持有收益 / 总成本
```

数量和总成本必须大于零。重复添加同一账户同一股票时，API 返回冲突和已有持仓 ID，界面转到编辑，不静默创建第二条记录。

### 8.2 基金快速录入

```text
总成本 = 当前持有金额 - 持有收益
```

- 当前持有金额必须大于零。
- 持有收益允许负数，但计算后的总成本必须大于零。
- 仅使用录入日期对应的官方单位净值推算份额，不使用估算净值。
- 找不到可靠官方净值时保存金额快照，`quantity` 保持空值并显示“待补份额”。
- 后续补到对应净值时可以生成推算份额，但必须保留原始金额和收益。

### 8.3 基金精确录入

```text
总成本 = 持有份额 × 平均成本
官方市值 = 持有份额 × 最新官方单位净值
官方持有收益 = 官方市值 - 总成本
```

若存在盘中估算净值，单只基金可额外展示“估算市值/估算收益”，但一期组合总资产只使用股票最新价格和基金官方净值，避免把官方口径与估算口径混成一个无标识数字。

## 9. API 契约

### 9.1 通用规则

- 基础路径：`/api/v1`
- 请求与响应字段：`camelCase`
- 枚举值：`UPPER_SNAKE`
- ID：UUID 字符串
- 日期：`YYYY-MM-DD`
- 时间：RFC 3339 UTC
- 金额、份额和价格：十进制字符串，前端禁止用 JavaScript `Number` 作为权威财务计算
- 列表端点：统一支持 `page`、`pageSize`，默认 20，最大 100
- PATCH：只修改出现的字段，并携带 `version`
- 所有错误使用同一结构

```json
{
  "error": {
    "code": "POSITION_ALREADY_EXISTS",
    "message": "该账户中已经存在此标的",
    "details": {
      "positionId": "4f9e1d63-7d3a-4ddd-8a8c-712a0a8a3bb4"
    },
    "requestId": "req_01J..."
  }
}
```

状态码：

- `400`：请求格式或状态不允许
- `401`：未登录或会话失效
- `403`：已登录但操作不允许
- `404`：资源不存在或不属于当前用户
- `409`：重复资源、版本冲突或非空删除
- `422`：字段语义校验失败
- `429`：注册、登录或重置请求过于频繁
- `500`：服务器错误，不暴露内部异常

### 9.2 端点清单

#### 认证

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/auth/registrations` | 邮箱密码注册 |
| POST | `/auth/sessions` | 登录并写入安全 Cookie |
| GET | `/auth/session` | 获取当前会话用户 |
| DELETE | `/auth/session` | 幂等退出 |
| POST | `/auth/password-reset-requests` | 请求邮件，始终返回统一结果 |
| POST | `/auth/password-resets` | 使用单次令牌设置新密码 |

#### 投资账户和持仓

| 方法 | 路径 | 说明 |
|---|---|---|
| GET/POST | `/investment-accounts` | 分页查询或创建账户 |
| GET/PATCH/DELETE | `/investment-accounts/{id}` | 查询、修改或删除空账户 |
| GET/POST | `/positions` | 查询或创建持仓 |
| GET/PATCH/DELETE | `/positions/{id}` | 查询、修改或删除持仓 |
| GET | `/position-summary` | 按账户筛选的组合汇总 |

#### 自选

| 方法 | 路径 | 说明 |
|---|---|---|
| GET/POST | `/watchlist-groups` | 查询或创建分组 |
| PATCH/DELETE | `/watchlist-groups/{id}` | 修改或删除空分组 |
| GET/POST | `/watchlist-items` | 按组查询或添加标的 |
| PATCH/DELETE | `/watchlist-items/{id}` | 修改备注、移动或删除 |

“转为持仓”由前端打开已有标的的持仓表单并调用 `POST /positions`；默认保留自选项，用户确认取消关注后再调用删除接口，避免一个跨资源接口产生隐藏副作用。

#### 资产与数据状态

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/instruments` | 按代码或名称搜索一期支持的资产 |
| GET | `/instruments/{id}` | 获取资产详情与最新定价状态 |
| GET | `/market-data/status` | 获取最近同步任务和数据新鲜度 |
| GET | `/health/live` | 进程存活检查 |
| GET | `/health/ready` | 数据库、迁移和必需配置检查 |

### 9.3 契约维护

- FastAPI 生成 OpenAPI 文档。
- CI 生成并校验 `openapi.json`。
- Web 端类型从 OpenAPI 生成，生成文件与后端契约一起评审。
- 已发布字段优先新增可选字段，不删除、不改类型；Breaking Change 需要新 API 版本和迁移说明。

### 10.2 持有页

桌面结构：

```text
┌──────────────────────────────────────────────────────────┐
│ 产品名       持有  自选                 搜索      用户菜单 │
├──────────────────────────────────────────────────────────┤
│ 持有                              [账户筛选] [添加持仓]    │
│ 总资产 ¥…   持仓成本 ¥…   持有收益 +¥… / +…%             │
│ 全部账户  证券账户  支付宝基金  长期账户                  │
├──────────────────────────────────────────────────────────┤
│ 资产       账户       份额/数量    最新价格    市值   收益 │
│ …                                                        │
└──────────────────────────────────────────────────────────┘
```

- 汇总采用一条“账本抬头”，不堆叠四个通用指标卡片。
- 账户使用水平筛选，不把账户误做成一级菜单。
- 股票和基金共享列表骨架，但字段标签按资产类型显示。
- 每行可展开查看数据来源、更新时间、原始录入方式和推算状态。
- 添加持仓先搜索资产，再选择账户和录入方式。

### 10.3 基金录入

```text
[快速录入]  当前持有金额 + 持有收益
[精确录入]  持有份额 + 总成本/平均成本
```

- 快速录入为默认选项。
- 表单下方实时展示计算预览，但保存时以后端结果为准。
- 份额来自推算时显示“估算份额”，没有净值时显示“暂不计算份额”。
- 错误文案直接说明如何修正，例如“持有收益不能使持仓成本小于等于 0”。

### 10.4 自选页

- 桌面端左侧为分组，右侧为标的列表；移动端使用顶部下拉选择分组。
- 列表展示名称、代码、资产类型、最新价格/净值、涨跌和更新时间。
- 备注为可选短文本，不加入目标价格、评分和推荐标签。
- “添加到持有”打开持仓表单，不自动删除自选。

### 10.5 移动端

- 底部固定导航只有“持有”和“自选”。
- 表格转换为紧凑卡片，金额和收益保持右对齐。
- 主要动作使用页面右下角单一添加按钮；不同时出现多个浮动按钮。
- 所有核心流程在 360px 宽度下可完成，无横向滚动。

## 11. 视觉系统

主题来自“个人账本”，但不模仿纸张、行情终端或旧产品。界面安静、数据密度适中，颜色只承担状态和操作含义。

### 11.1 设计令牌

```css
:root {
  --canvas: #f3f6f5;
  --surface: #ffffff;
  --ink: #13231d;
  --muted: #607068;
  --line: #d7e0dc;
  --accent: #285f4d;
  --gain: #b33a32;
  --loss: #14705c;
  --warning: #8a5a18;
}
```

- 正文字体使用本机中文系统字体栈，避免外部字体拖慢首屏。
- 金额与份额使用等宽数字和 `font-variant-numeric: tabular-nums`。
- 盈利使用红色、亏损使用绿色，符合中国市场习惯；同时显示正负号和文字，不只依赖颜色。
- 阴影只用于临时浮层，常规信息用边线和留白分层。
- 不使用渐变、玻璃拟态和装饰性大图。

### 11.2 标志性交互

持仓行提供一条细小的“成本—现值刻度”：成本点固定，当前值在左右移动，并配合明确数字。它把账本中最重要的关系变成可扫读信息，又不引入完整图表。

该刻度只作为辅助，数值和正负状态仍完整展示；当用户选择减少动态效果时取消过渡动画。

## 12. 认证与安全设计

- 密码使用 Argon2id 哈希，绝不记录明文。
- 密码长度 12–128 个字符，允许密码管理器粘贴，不强制周期更换。
- 会话令牌使用安全随机数，数据库仅保存令牌哈希。
- Cookie 设置 `Secure`、`HttpOnly`、`SameSite=Lax`，生产域名限定 Host。
- 状态变更请求校验 Origin，并使用 CSRF Token 请求头。
- 登录、注册和密码重置进行 IP 与主体维度限流。
- 密码重置令牌 30 分钟失效、单次使用，发送请求始终返回相同文案，防止枚举邮箱。
- 认证成功后轮换会话；修改密码后撤销其他会话。
- Repository 方法必须接收当前用户 ID，并通过账户或分组归属过滤。
- 对“不存在”和“不属于当前用户”的资源统一返回 404，减少资源枚举。
- 日志不记录密码、Cookie、重置令牌、完整邮箱和用户持仓金额。
- 当前 Caddy Basic Auth 在应用认证验收通过前保留，验收后一次性移除，避免双重登录长期存在。

## 13. 行情任务与加载性能

### 13.1 数据同步

- 每日同步 A 股和公募基金主数据。
- 交易时段只批量刷新用户持有和自选涉及的股票、ETF、LOF 与基金估算净值。
- 晚间循环刷新基金官方净值，按基金实际净值日期入库。
- 使用 PostgreSQL advisory lock 防止多个 Worker 重复执行同一任务。
- 每次任务记录状态、数量、来源、耗时和错误摘要。
- Provider 超时、限流或字段异常时保留上一条有效数据并标记陈旧，不覆盖成空值。

具体刷新频率通过环境变量配置，不写死为产品承诺。

### 13.2 前端性能

- React 首屏只请求当前页面汇总和第一页列表。
- TanStack Query 在标签页可见时轮询本地 API，页面隐藏时停止。
- Nginx 对带内容哈希的静态资源设置长期缓存，HTML 不长期缓存。
- 用户私有 API 响应设置 `Cache-Control: no-store`。
- 不在首屏加载图表库、富文本编辑器或外部字体。

性能验收目标：

- 持有/自选读取接口在 100 条数据规模下，预热后 P95 小于 300ms。
- 模拟快速 4G 时 LCP 小于 2.5s、CLS 小于 0.1、INP 小于 200ms。
- 首屏关键 JavaScript gzip 后不超过 250KB。
- 页面读取流程不存在同步外部行情网络请求。

## 15. 代码风格

### 15.1 Python

- 完整类型标注，Pydantic 只用于边界模型，SQLAlchemy 模型不直接作为 API 响应。
- 类和方法必须有清晰中文文档注释；普通语句只在解释业务背景或非显而易见取舍时注释。
- 财务计算只使用 `Decimal`。
- Service 负责业务规则，Repository 负责持久化，Router 不写业务逻辑。

```python
class PositionService:
    """处理持仓录入、规范化和用户权限边界。"""

    def create_fund_position(
        self,
        user_id: UUID,
        command: CreateFundPositionCommand,
    ) -> Position:
        """根据基金录入模式生成唯一、可审计的持仓。"""
        normalized = self._normalizer.normalize(command)
        return self._repository.create_for_user(user_id, normalized)
```

### 15.2 TypeScript

- 开启 `strict`，禁止 `any` 逃逸。
- 页面不直接拼接 URL，所有请求经过生成的 API Client。
- 服务端金额以字符串接收，展示和预览使用十进制库，不用浮点数作为权威结果。
- 导出的组件和业务 Hook 使用清晰中文注释说明职责。

```typescript
type FundPositionInput =
  | { mode: "FUND_AMOUNT"; currentValue: string; holdingProfit: string }
  | { mode: "FUND_SHARES"; quantity: string; totalCost: string };

/** 提交基金持仓，并以后端返回的规范化结果更新缓存。 */
async function createFundPosition(input: FundPositionInput): Promise<Position> {
  return apiClient.positions.create(input);
}
```

提交说明使用 Conventional Commits 类型和中文描述，例如：`feat: 增加基金快速录入`。实际 commit、merge、push 必须先取得用户明确授权。

## 18. Git、版本与开源工程规范

### 18.1 分支模型

```text
main
  └── dev2.x                 # 2.x 集成分支，首次集成时从 main 创建
       ├── feature/...
       ├── fix/...
       └── chore/...
```

当前 `feature/portfolio-watchlist-v2` 已从 `main` 创建。首次集成流程：

1. feature 完成全部 CI、代码评审和人工验收。
2. 用户明确授权后，从 `main` 创建 `dev2.x`。
3. 通过 PR/评审将 feature 合并到 `dev2.x`。
4. 后续 2.x 功能分支全部从 `dev2.x` 创建并保持短生命周期。
5. `dev2.x` 稳定后通过发布 PR 合并到 `main`，创建 `v2.0.0` 标签。

`dev2.x` 是用户指定的长期集成分支。为降低长期分支风险，每个 feature 保持小而短，定期同步 `dev2.x`，不在 `dev2.x` 直接开发。

### 18.2 合并门禁

- 禁止直接推送和强制推送到 `dev2.x`、`main`。
- 至少一次代码评审通过。
- 后端 lint、类型检查、测试和覆盖率通过。
- 前端 lint、类型检查、测试、构建和 E2E 通过。
- 数据库迁移检查、OpenAPI 契约检查和容器构建通过。
- 依赖安全扫描无未处理的高危问题。
- PR 必须填写变更目的、测试证据、风险、回滚和 Breaking Change。

### 18.3 开源仓库文件

一期提供：

- `README.md`：定位、截图、功能、快速启动、架构、数据来源、免责声明。
- `CONTRIBUTING.md`：开发环境、分支、提交、测试和 PR 流程。
- `CODE_OF_CONDUCT.md`：贡献者行为准则。
- `SECURITY.md`：漏洞报告方式、支持版本和响应流程。
- `CHANGELOG.md`：按 Keep a Changelog 记录版本变化。
- `LICENSE`：等待用户确认许可证后加入。
- Issue 表单：Bug、功能建议和数据源故障。
- PR 模板：验收、测试、安全、兼容性和截图。
- GitHub Actions：CI、依赖审查、容器扫描和发布检查。
- Dependabot：npm、Python 和 GitHub Actions 依赖更新。

版本遵循 Semantic Versioning：新产品首个稳定版本为 `v2.0.0`。`main` 始终对应可部署版本，`dev2.x` 不打稳定标签。

### 18.4 开源安全边界

## 20. 行为边界

### 始终执行

- 先更新规格和测试，再改变业务行为。
- 验证所有外部输入、第三方数据和环境变量。
- 所有数据库查询包含用户归属边界。
- 运行 lint、类型检查、测试和构建。
- 变更保持小批次并提供验证证据。
- 保持新增字段向后兼容，财务数据使用 Decimal。

### 必须先询问

- 新增生产依赖或基础设施服务。
- 修改数据库已发布字段、删除表或执行数据迁移。
- 改变公开 API 契约、认证方式或 Cookie 策略。
- 删除旧代码、切换域名、移除 Basic Auth 或恢复生产备份。
- 创建许可证、公开仓库、创建 Git 提交、合并或推送。

### 绝不执行

- 提交密钥、真实持仓、数据库或备份。
- 为让测试通过而删除测试、降低安全校验或伪造行情数据。
- 使用客户端传入的用户 ID 判定数据归属。
- 在未备份和验证时执行破坏性数据库操作。
- 未经授权直接向 `dev2.x` 或 `main` 推送。

## 22. 风险与缓解

| 风险 | 缓解措施 |
|---|---|
| 免费行情延迟、限流或字段变化 | Provider 隔离、响应校验、任务留痕、陈旧标记和可替换数据源 |
| 开放注册遭遇撞库或批量请求 | Argon2id、安全会话、CSRF、限流、统一错误和安全事件日志 |
| 邮箱未验证导致输错地址 | 注册时二次确认邮箱、提供修改入口、重置邮件不泄露账户存在性 |
| 新旧系统切换失败 | 独立端口、旧服务保留、Caddy 原子切换和回滚演练 |
| `dev2.x` 长期分支积累冲突 | feature 小批次、短生命周期、禁止直接开发、持续同步和 CI 门禁 |
| 开源仓库泄露隐私或密钥 | 示例数据虚构、历史扫描、严格 ignore、PR 安全检查 |
