# 个人股票与基金持仓工具：实施计划

> 状态：Spec-Driven Development / PLAN 终版，用户已于 2026-08-24 确认
> 当前分支：`feature/portfolio-watchlist-v2`
> 本文只定义阶段、依赖和验证门，不授权编码、提交、合并或推送。

## 1. 计划目标

按可独立验证的纵向功能切片建设新系统，始终保持旧 Streamlit 服务和数据不受影响。每个阶段都必须完成代码、测试、文档和验证，不能等到最后再集中补测试或连接前后端。

完成本计划后应达到：

- 新产品在本地和服务器独立端口可完整运行。
- 注册登录、投资账户、股票/基金持仓、自选分组和密码重置流程通过。
- 性能、安全、开源工程和部署门禁通过。
- feature 分支具备合并到 `dev2.x` 的条件。
- 未经用户确认，不执行 Git commit、merge 或 push。

## 2. 依赖关系

```text
开源仓库与工程骨架
  │
  ├── Web/API/数据库可启动
  │     │
  │     ├── 认证与用户隔离
  │     │     └── 投资账户
  │     │
  │     └── 资产主数据与行情 Provider
  │           ├── 股票/基金持仓
  │           └── 自选分组
  │
  ├── OpenAPI 契约与前端 Client
  │     ├── 持有页面
  │     └── 自选页面
  │
  └── 全链路测试与部署
        ├── 服务器并行验证
        ├── Caddy 切换演练
        └── feature -> dev2.x 集成评审
```

认证和数据库基础必须先稳定；资产主数据必须在持仓和自选前可搜索；持仓和自选可以在公共契约冻结后独立推进；部署只能在所有本地门禁完成后开始。

## 3. 阶段 0：开源工程与双栈骨架

### 目标

建立不影响旧系统的新工程入口，使空应用可以通过统一命令启动、测试和构建。

### 主要产出

- Apache-2.0 `LICENSE`。
- README、贡献指南、行为准则、安全政策和变更日志骨架。
- Issue/PR 模板、Dependabot 和基础 GitHub Actions。
- `apps/api`、`apps/web`、`compose.v2.yaml`、`.env.v2.example` 和 `Makefile`。
- FastAPI 存活接口、React 空壳路由、PostgreSQL 连接和 Alembic 基线。
- Ruff、mypy、pytest、ESLint、TypeScript、Vitest 和构建命令。

### 验证门

- `docker compose -f compose.v2.yaml config` 通过。
- Web、API、PostgreSQL 可以同时启动，旧 `compose.yaml` 不变。
- 后端 lint、类型检查和空测试通过。
- 前端 lint、类型检查、测试和构建通过。
- 仓库不包含 `.env`、数据库、密钥和构建产物。

### 主要风险

- 根目录配置与旧 Python 工程冲突：新依赖和工具全部放入 `apps`，根目录只提供编排入口。
- CI 过早复杂化：阶段 0 只建立必要门禁，安全扫描和 E2E 在后续阶段增强。

## 4. 阶段 1：认证与用户隔离纵向切片

### 目标

交付可实际使用的注册、登录、退出和当前会话流程，并建立后续所有业务模块的用户隔离基础。

### 主要产出

- `users`、`sessions`、`security_events` 首批迁移。
- Argon2id 密码哈希、服务端不透明会话和安全 Cookie。
- 注册、登录、当前会话和退出 API。
- 注册页、登录页、受保护路由和用户菜单。
- 统一 API 错误结构、请求 ID、Origin/CSRF 校验和基础限流。
- OpenAPI 生成与 Web 类型 Client。

### 验证门

- 注册、登录、退出和会话过期 API 测试通过。
- 重复邮箱、错误密码和未登录访问返回约定错误。
- 数据库只保存密码哈希和会话令牌哈希。
- 两个测试用户的会话不能互换。
- 浏览器完成注册、登录、刷新保持会话和退出。

### 主要风险

- Cookie 在本地 HTTP 和生产 HTTPS 行为不同：配置显式区分开发与生产，并在 E2E 中覆盖。
- 错误信息泄露账户存在性：登录与重置使用统一文案和响应耗时策略。

## 5. 阶段 2：密码重置与投资账户纵向切片

### 目标

完成账户体系闭环，并让用户可以创建和管理多个投资账户。

### 主要产出

- `password_reset_tokens`、`investment_accounts` 迁移。
- SMTP 适配器、密码重置请求和单次令牌消费。
- 忘记密码和重置密码页面。
- 投资账户查询、创建、重命名、排序和删除空账户 API。
- 注册后自动创建默认投资账户。
- 用户菜单中的投资账户管理界面。

### 验证门

- 重置请求不泄露邮箱是否存在。
- 令牌过期、重复使用和修改密码后撤销其他会话测试通过。
- 用户甲不能读取或修改用户乙的投资账户。
- 非空删除约束先以契约测试固定，持仓阶段启用实际数据场景。
- SMTP 使用测试替身，测试环境不发送真实邮件。

### 主要风险

- 生产 SMTP 尚未配置：本地使用捕获邮件服务，服务器上线前把 SMTP 纳入 readiness 检查。

## 6. 阶段 3：资产主数据与行情读取链路

### 目标

让用户可以可靠搜索一期支持的 A 股和国内基金，并让页面只读取本地数据库行情。

### 主要产出

- `instruments`、`instrument_prices`、`data_sync_runs` 迁移。
- 股票、基金主数据和价格 Provider 契约。
- 外部响应 Pydantic 校验、超时、重试、回退和错误留痕。
- 资产搜索、详情、最新定价和市场数据状态 API。
- Worker 运行入口、调度配置和 PostgreSQL advisory lock。
- 资产搜索对话框及价格类型、来源、更新时间组件。

### 验证门

- 资产以类型、市场和代码联合唯一。
- 股票价格、基金官方净值和估算净值分别入库。
- 外部字段缺失或类型异常时拒绝写入。
- 页面 API 不触发外部 HTTP 请求。
- 旧数据存在时，Provider 失败后页面展示陈旧状态而不是空数据或伪实时。

### 主要风险

- 免费数据源变化频繁：先实现稳定契约与测试样本，再接真实源；真实联网测试与离线测试分开。
- 全量同步耗时：主数据低频同步，交易时段只刷新持有和自选相关标的。

## 7. 阶段 4：股票持仓纵向切片

### 目标

完成第一个真正可用的业务闭环：用户可以在不同投资账户管理股票持仓和查看汇总。

### 主要产出

- `positions` 迁移和同账户同标的唯一约束。
- 股票数量、总成本/平均成本、Decimal 估值和收益规则。
- 持仓查询、创建、修改、移动、删除和汇总 API。
- 乐观锁版本冲突和重复持仓错误。
- 持有页抬头、账户筛选、桌面列表、移动卡片和添加/编辑表单。

### 验证门

- 数量、成本、市值、持有收益和收益率由测试精确复算。
- 重复添加进入编辑路径，不产生第二条记录。
- 非空投资账户删除返回约定冲突。
- 用户隔离覆盖查询、创建、修改、移动和删除。
- 360px 与桌面浏览器均能完成股票持仓流程。

### 主要风险

- 金额展示和输入舍入不一致：后端 Decimal 为权威，API 使用字符串，前端只进行十进制预览。

## 8. 阶段 5：基金双录入纵向切片

### 目标

在已有持仓骨架上完成基金快速录入和精确录入，并保证官方净值与估算净值不混用。

### 主要产出

- `FUND_AMOUNT` 与 `FUND_SHARES` 判别式输入契约。
- 原始输入、规范化成本、推算份额和推算依据保存。
- 对应官方净值缺失时的金额快照状态。
- 快速/精确切换表单、计算预览和“估算份额/待补份额”提示。
- 单只基金官方估值和可选盘中估算展示。

### 验证门

- 正收益、零收益、负收益和非法负成本测试通过。
- 只有官方单位净值可用于推算份额。
- 净值缺失时能够保存快照，但不会伪造数量。
- 总成本、份额、平均成本和官方市值计算正确。
- 组合总资产不混入未标识的基金盘中估算值。

### 主要风险

- QDII 和特殊基金净值日期延迟：所有计算使用实际净值日期，页面不写“今日净值”。

## 9. 阶段 6：自选分组纵向切片

### 目标

交付第二个一级业务入口，让用户按多个分组管理观察中的股票和基金。

### 主要产出

- `watchlist_groups`、`watchlist_items` 迁移。
- 默认分组、分组排序、非空删除和组内唯一约束。
- 自选分组和标的 CRUD、移动与备注 API。
- 自选页桌面双栏、移动分组选择和添加资产流程。
- “添加到持有”打开持仓表单，默认保留自选项。

### 验证门

- 同一标的可存在不同分组，但不能在同组重复。
- 默认分组不可删除，非空分组删除被阻止。
- 用户甲不能查看或移动用户乙的自选项。
- 股票和基金均展示正确价格类型、来源和时间。
- 从自选添加持仓不会产生隐藏删除副作用。

## 10. 阶段 7：体验、性能与安全收口

### 目标

把纵向功能切片收敛成一个简洁、一致、快速且可公开部署的产品。

### 主要产出

- 全局设计令牌、成本—现值刻度、空状态、错误状态和加载骨架。
- 键盘导航、焦点管理、屏幕阅读器标签和减少动态效果支持。
- 前端按路由分包、静态缓存和 API no-store 策略。
- 认证限流增强、安全日志脱敏和依赖安全扫描。
- 完整 OpenAPI 契约检查、迁移检查和浏览器 E2E。
- README 截图、快速启动、架构、数据源和投资免责声明。

### 验证门

- 100 条持仓/自选数据下读取接口预热后 P95 小于 300ms。
- 模拟快速 4G：LCP 小于 2.5s、CLS 小于 0.1、INP 小于 200ms。
- 首屏关键 JavaScript gzip 后不超过 250KB。
- 后端和前端整体覆盖率不低于 80%，认证、权限和计算分支覆盖率不低于 90%。
- 自动可访问性检查和核心键盘流程通过。
- 无未处理的高危依赖漏洞。

## 11. 阶段 8：服务器并行部署与发布准备

### 目标

在不影响旧域名服务的前提下验证新系统，并形成可执行回滚路径。

### 主要产出

- 新 Web、API、Worker 和 PostgreSQL 独立 Compose 部署。
- Alembic 升级、readiness、日志和 `pg_dump` 备份恢复脚本。
- Caddy 新路由草案、Basic Auth 移除步骤和回滚配置。
- 服务器完整 E2E、性能冒烟和回滚演练记录。
- `CHANGELOG` 的 `v2.0.0` 发布说明草案。

### 验证门

- 旧 Streamlit 服务、SQLite 和卷保持可用。
- 新系统独立端口完成注册、登录、密码重置、持有和自选流程。
- PostgreSQL 备份可恢复到临时数据库。
- Caddy 切换和回滚步骤在不删卷的情况下验证。
- 未经用户授权，不实际切域名、不移除 Basic Auth。

## 12. 阶段 9：feature 集成到 dev2.x

### 前置条件

- 阶段 0–8 所有验证门通过。
- 多角色代码评审没有未解决的 Critical/High 问题。
- 用户确认实际提交、创建 `dev2.x` 和合并。

### 集成顺序

1. 展示完整 diff、测试报告、安全扫描、Breaking Change 和回滚说明。
2. 获得用户明确授权后，按逻辑切片创建中文 Conventional Commits。
3. 从 `main` 创建当前不存在的 `dev2.x`。
4. 通过 PR 或等价评审将 feature 合并到 `dev2.x`。
5. 在 `dev2.x` 再运行全量 CI 和服务器并行验收。
6. `dev2.x` 稳定后另行申请合并 `main` 和发布 `v2.0.0` 的授权。

本计划不包含现在创建 `dev2.x`，也不包含现在提交、合并或推送。

## 14. 可并行与必须串行的工作

### 契约冻结后可并行

- 后端服务实现与前端静态组件。
- 离线 Provider 契约测试与页面空/错/加载状态。
- 开源文档与不依赖业务代码的 CI 配置。
- 已完成模块的安全测试和可访问性测试。

### 必须串行

- Alembic 迁移链。
- 认证和用户隔离基础。
- OpenAPI 契约变更与生成 Client。
- Caddy 域名切换和回滚。
- feature 到 `dev2.x` 的创建与合并。

即使执行时采用并行工作，也必须先冻结共享契约，最终由单一集成流程验证，避免多个工作流同时修改同一迁移或公共类型。

## 15. 风险排序

| 风险 | 等级 | 处理阶段 | 缓解措施 |
|---|---|---|---|
| 用户数据越权 | Critical | 1–6 | 服务端用户归属、统一 Repository 签名、跨用户负向测试 |
| 财务计算或净值口径错误 | Critical | 3–5 | Decimal、判别式输入、固定样例和 Provider 契约测试 |
| 公开注册认证攻击 | High | 1–2、7 | Argon2id、安全 Cookie、CSRF、限流和统一错误 |
| 免费行情接口不稳定 | High | 3、7 | 本地缓存、异步任务、回退、陈旧标记和可替换 Provider |
| 新旧服务切换失败 | High | 8 | 独立端口、旧服务保留、备份和 Caddy 回滚演练 |
| `dev2.x` 长期分支冲突 | Medium | 9 以后 | 短 feature、CI 门禁、定期同步、禁止直接开发 |
| 开源仓库泄密 | High | 0、7 | ignore、秘密扫描、虚构样例、PR 安全清单 |

## 16. 计划审批后下一步

用户批准本计划后，进入 Spec-Driven Development 的 TASKS 阶段：把每个阶段拆成单次会话可完成、最多约 5 个文件的具体任务，每项包含验收条件、验证命令和依赖。任务清单再次经用户批准后，才进入 TDD 编码。

## 17. 开放问题

无技术开放问题。实施过程中若第三方行情源、SMTP 或服务器实际环境与设计不符，必须先更新规格并向用户确认，不在代码里猜测处理。
